# Ofertas Leonix Ad ID Coordination

## Required Format

Canonical public ad ID format:

```text
LNX-XXXXXXXX
```

The eight-character suffix must be generated by the shared listing identity system and must be unique across authoritative Leonix public listings.

## Parent Relationship

The Ofertas/Cupones parent listing has one Leonix Ad ID. The ID belongs to the parent row and must be preserved across:

- edit
- correction
- resubmission
- asset replacement
- approval/rejection
- expiration
- renewal/republish unless shared lifecycle explicitly creates a linked renewal identity

Extracted products/items must not receive fabricated child Leonix IDs in category-local code. Future product identity can exist only if global architecture defines it.

## Generation Timing

Recommended generation event:

- Generate when the canonical parent listing is first created or when paid fulfillment binds the parent to a public listing identity.
- Never let the browser generate the authoritative ID.
- Do not generate a new ID on owner correction/resubmission.

## Persistence Requirement

The ID must be stored in a shared/schema-backed field that public, owner, admin, and search mappers can read consistently. Current Package 3 code did not find `leonix_ad_id` in Ofertas runtime paths, so this remains shared implementation work.

## Surface Behavior

Preview:

- Show "pending Leonix Ad ID" only if the ID is not yet generated.
- Do not show a fake ID.

Owner dashboard:

- Show the real parent Leonix Ad ID when available.
- Keep the same ID after correction/resubmission.

Admin:

- Show parent database ID and Leonix Ad ID.
- Allow search/filter by either identifier once shared query support exists.

Public:

- Show the real Leonix Ad ID when available.
- Do not expose owner-only identity fields.

Search:

- Public search results and detail surfaces should carry the parent Leonix Ad ID for analytics and user reference when available.
- Child product search rows should relate back to the same parent Leonix Ad ID.

Cupones:

- Coupon parents follow the same parent Leonix Ad ID contract.
- Coupons do not fabricate product/cart/list identities.

## Shared Needs

Schema/migration need:

- Add or confirm a persisted parent-level `leonix_ad_id` field for `ofertas_locales`.
- Enforce uniqueness.
- Backfill only by shared identity rules.

Mapper/API need:

- Include real Leonix Ad ID in owner/admin/public category projections.
- Include it in analytics payloads when available.
- Keep `id` as database identity and `leonix_ad_id` as public ad identity.

Likely shared files:

- `app/lib/listingIdentity/**`
- `app/lib/analytics/listingAnalyticsIdentity.ts`
- `app/lib/analytics/server/resolveListingAnalyticsIdentity.ts`
- `supabase/migrations/**`
- Ofertas category mappers after schema is available.

## Tests

- New parent receives exactly one `LNX-XXXXXXXX` ID.
- Duplicate ID insert/update is rejected.
- Owner correction keeps the same parent and same Leonix Ad ID.
- Asset replacement keeps the same parent and same Leonix Ad ID.
- Public API exposes only real stored ID.
- Child product rows resolve to the parent ID and do not invent child IDs.
- Coupon parents behave the same as flyer parents.
