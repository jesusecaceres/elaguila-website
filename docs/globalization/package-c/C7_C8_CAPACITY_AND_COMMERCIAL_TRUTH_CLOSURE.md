## 3. Architecture plan corrections (Coach review — full text in the plan file)

1. **RPC must derive capacity, not accept `p_limit`.** Both RPCs independently re-derive the effective limit from a parent-scoped `listing_package_entitlements` lookup (`status='active' AND revoked_at IS NULL AND (starts_at IS NULL OR starts_at<=now()) AND (ends_at IS NULL OR ends_at>=now())`), never a caller-supplied number.
2. **Autos new child create must be atomic.** Confirmed the existing schema already inserts every new Autos row as `status:"draft"` (non-capacity-consuming) — chose Option A (insert-as-draft, then a separate atomic activation RPC) over a mega-transaction, requiring zero insert-path change.
3. **RPC must enforce subscription lifecycle.** Both RPCs independently query `leonix_subscription_records` under the same advisory lock, denying `grace`/`suspended`/`canceled`, permitting `none`/`pending`/`active` — reusing the exact C2/C3 model, never a new one. First-payment ordering verified by direct code read (`webhook/route.ts:103-126`): inventory activation runs before subscription-record creation in the same delivery, so the very first activation always sees `v_sub_status IS NULL` and must be permitted.
4. **Idempotent duplicate delivery.** An already-active target returns `activated=true, idempotent=true` before acquiring the lock or re-counting — never a second consumed slot, never a forced destructive transition.

## 5. C7 — parent-scoped capacity + atomic activation (Gates 1-5)

**Identity/counting model (§E/§F of the plan, unchanged from freeze):** Autos parent = `inventory_role='main'`, group = `COALESCE(dealer_inventory_group_id, dealer_inventory_parent_listing_id, id)`; Bienes parent = `inventory_role='main'`, child linkage = `br_inventory_parent_listing_id`. Both categories count the parent row itself as one of the included slots (the owner-confirmed model, unchanged).

**Migration (`supabase/migrations/20260810120000_autos_br_negocio_capacity_activation_rpc.sql`):** two additive SECURITY DEFINER functions, `autos_dealer_activate_listing`/`br_negocio_activate_listing`. Each: re-fetches the target row `FOR UPDATE`; short-circuits idempotently if already active; derives the parent from the target's own linkage column; acquires a category-namespaced `pg_advisory_xact_lock` keyed by group/parent id; checks subscription lifecycle; derives the entitlement-based limit; counts active siblings+parent under the lock; conditionally activates. A legacy-data edge case was found and fixed during implementation: `inventory_role IS NULL` (pre-grouping-migration rows) is treated as self-parent (`IS DISTINCT FROM 'inventory_vehicle'`/`'inventory_property'`) rather than incorrectly rejected. Structural/textual verification only (`scripts/verify-c7-capacity-rpc-sql-contract.mjs`, 18 checks) — the migration is never applied to any database in this build, matching every prior build's convention; live concurrency certification is explicitly deferred to a separate, later, controlled migration-certification gate.

**Application preflight (`commercialWriteGuard.ts`):** Autos counting is now group-scoped (reusing the pre-existing, previously-unused `resolveDealerInventoryGroupingKey`/`countActiveDealerInventoryVehicles`); `childListingId` is DB-verified (ownership + parent linkage + role) for both categories before being trusted, with an explicit skip when the child IS the parent restoring itself (a self-reference edge case found during implementation). This guard is now documented as advisory/UX-only — the RPC is the sole financial authority.

**Mutation-path adoption (Gate 4):** every real capacity-increasing write for both categories — Autos: dashboard restore, admin restore/unsuspend/republish-reactivation, Stripe/webhook/verify activation (via `tryActivateAutosListingAfterPayment`), QA bundle publish; Bienes: payment activation (incl. sibling fan-out), resume, admin unsuspend/republish-reactivation — now calls `activateAutosDealerListingAtomic`/`activateBrNegocioListingAtomic` instead of a bare `.update({status:'active'})`. The dead, boost-unaware `canActivateDealerListing` function was deleted outright.

**Two real defects found and closed beyond the original plan's evidence (Gate 5):**
- **Bienes insert-time bypass.** `AgenteIndividualResidencialPreviewClient.tsx`'s "add inventory property" flow (covered by an existing pack, no new Stripe session needed) was inserting the new row **directly as `status:'active'`** (`activationMode:"immediate"`), bypassing the RPC entirely and protected only by a spoofable client-side count check — contradicting the frozen plan's explicit assumption that Bienes never inserts as active. Closed by always inserting `pending`, then activating through a new, narrowly-scoped `activate_pending` BR lifecycle mutation (same RPC, same capacity/lifecycle enforcement as Resume, distinct required prior state).
- **Dashboard detail-page bypass.** `mis-anuncios/[id]/page.tsx`'s `resumeListing()` performed an unconditional direct client-side write for every category, unlike the sibling list page which already routes Bienes negocio rows through the safe server lifecycle route. Closed by gating it the same way.

A third, adjacent finding — the single-listing detail page's "Reactivate" button can revive a `sold` Bienes row via the same unconditional direct write, and the BR lifecycle service currently treats `sold` as terminal by design — was deliberately **not** absorbed into this build (it requires a scoped UX/authorization decision, not a mechanical capacity fix) and is flagged as a separate follow-up. A fourth finding — the Autos dashboard's top-level "X/10 used" summary (`GET /api/clasificados/autos/listings`) is still computed owner-wide rather than group-scoped, a display-only (non-enforcing) echo of the same original pooling defect — is likewise flagged as a separate follow-up rather than absorbed here, since the correct per-group breakdown is already displayed elsewhere on the same page and fixing the aggregate requires a UX decision about which group a multi-group owner's single summary should represent.
